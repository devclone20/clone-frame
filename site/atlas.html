ATLAS — the Harness Architect

devclone20/atlas_corporation_okx_ai — MIT · public monorepo OKX agent #4460 · X Layer 8 A2A services ATLAS #1 · Base soul sealed · Irys

The next decade of agent software will not be operated — it will be supervised. ATLAS is a step into that world, and it sells exactly one thing: the Harness Architecture. You describe a problem, a service idea or a project; ATLAS researches the domain and delivers the complete design of the dedicated agent team that will solve it — named agents with roles and hard tool allowlists, workflows with exit-state tokens, non-collapsible quality gates, real, verified data sources, schedules, and step-by-step build instructions. The client hands that document to any LLM coding agent — Claude Code, ChatGPT, DeepSeek — and gets a running, supervised team. Not once. Permanently.

ATLAS is an iNFT: the ATLAS #1 token on Base is the agent's identity, and its soul — a four-lobe neural_soul.md — is sealed on Irys, every version stored permanently behind a mutable anchor the owner can refine. Own the token, own the agent, its treasury and its reputation. One transfer moves everything.

The one-line thesis. Most agents sell answers; an answer dies at the end of the chat. ATLAS sells the blueprint of the team that keeps answering — a deterministic harness with a language model attached, where the model proposes, the harness disposes, and anything irreversible sits behind policy no prompt can override.

The product · a Harness Architecture

Every ATLAS deliverable is one Markdown document on a fixed skeleton of up to fourteen sections — twelve always present: overview, executive summary, problem analysis, data sources (real endpoints, verified, with formats, auth and licences), the team — a roster of named agents plus one full role-contract file per agent, ready to save as crew/<name>.md — workflows with exit-state tokens, the quality gates, schedules and anti-dormancy rules, the event-log and audit design, step-by-step build instructions, acceptance tests, and a maintenance story. Money & custody and open-items sections appear only when the problem calls for them.

Fig. 1 — The product is the blueprint. ATLAS designs; your LLM builds; the team runs — permanently.

ATLAS sells on the OKX AI marketplace today — agent #4460 on X Layer, escrow-settled A2A jobs, no public API surface at all. Virtuals ACP on Base is the planned second rail: a second intake into the same architect, with wallets, nonce spaces and reputation kept strictly separate.

The Harness

A Harness is a supervised crew of agents running a loop that does not stall: Plan → Work → Verify → Settle → Re-plan. Every crew member is a role contract as a file — a hard tools allowlist plus an explicit MUST-NOT block — and every handoff is a named exit-state token. The language model is a component inside the harness: it proposes plans and typed intents, but it is structurally incapable of anything irreversible, because that lives on the far side of gates it cannot reach. This grammar governs ATLAS itself, and it is written into every architecture ATLAS ships.

Four gates sit on the path from work to the world. Treasury exists only when value moves — but where a gate exists it can never be collapsed into the role it judges, and never skipped: the actor may never also be the judge. They are invariants, enforced by the harness, not by a prompt:

Fig. 2 — The four non-collapsible gates: Evaluator · Safety · Treasury · Owner. Anything irreversible is downstream; the model never reaches it.

The canonical crew taxonomy has seven mandatory roles — Orchestrator (the only planner), Research (never fabricates a number), Delivery (the value producer), Evaluator (no write tools), Safety (veto, fail-closed), Ops, and the human Owner (final authority) — plus Treasury, Content and Job-Hunter when the problem calls for money, a public voice or a marketplace intake. Every generated architecture picks from this taxonomy, names each agent, and binds it to the same event-log discipline and, when value moves, the same fourteen invariants.

The Oracle · the architect's eye

The hardest question in this trade is not "how do I build an agent?" but "what shape of team does this problem deserve?" That is the Oracle — ATLAS's design faculty: it sees the space of possible Harnesses as a map and picks the shape. Given a problem, it decides which roles the crew needs and which can fuse, which of the four gates apply (a team that moves no money needs no Treasury), which data sources are load-bearing, and what cadence keeps the loop alive. Every choice is written down and justified in the deliverable — the Oracle decides, the document shows its work.

Fig. 3 — The Oracle shapes; the grammar constrains. Same problem, different risk surface — different Harness.

The Engine

One engine, open source: apps/architect in the public monorepo. It turns an intake — a plain-text brief, a filled template, or JSON — into a finished architecture through a fixed pipeline. Before a document leaves the building, the deterministic validator checks every required skeleton section, the presence of the gates and of role-contract files, and screens the copy against the never-list's hardest rule — an architecture may never promise earnings. The deeper laws — real, verified endpoints only; no LLM in a signing path — are written into the authoring grammar and checked by the evaluator review behind it.

Fig. 4 — The architect pipeline. Change the grammar in one place and every future deliverable changes with it.

One repo, everything ATLAS

ATLAS lives in a single public monorepo — because the agent is an iNFT, and an iNFT's metadata deserves one canonical address, not a scatter of repositories. apps/architect is the engine; apps/runtime is the deployment (brain memory, systemd units, an idempotent deploy script); packages/blueprint is the grammar — the authoring spec and the fourteen-section skeleton every deliverable must satisfy; packages/catalog is the marketplace offer; deliverables/samples holds the proof. Every future CLONE FRAME agent will follow the same rule: one agent, one monorepo.

The Committee

A delivery is a claim, and claims are cheap. ATLAS makes them expensive to get wrong: every architecture passes the deterministic structural validator (all required skeleton sections present, gates and role-contract files included, no earnings promises) and an independent evaluator review before it ships — and for high-stakes work, a committee of ≥2 evaluators under quorum, none of whom wrote the document. The actor is never the judge. On OKX the point is sharpened by economics: a rejected delivery can go to a dispute arbitrated by a staked network of evaluators, and a lost dispute means the escrow returns to the buyer. Quality is not a virtue here; it is enforced.

Fig. 5 — No architecture ships unvalidated. On OKX, a lost dispute returns the escrow — the gate pays for itself.

Bounded autonomy · security

Autonomy here does not mean "sign whatever the model suggests." It means deterministic wallet policy plus no LLM in the signing path. The model can propose any intent it likes; the policy engine — pure, deterministic code — decides whether it may become a signature. Two rules bound every outbound movement:

  • A $100-per-day transfer policy on the operating wallet — even a fully compromised brain is bounded per day.
  • A destination whitelist to the owner's cold wallet, set as wallet policy — and, by standing rule, any large or novel outbound transfer is owner-gated before it happens.

Deposits are inbound and unaffected: ATLAS can always receive. This is least-privilege applied to money: the blast radius of any failure — prompt injection, a jailbroken plan, a bad engine — is capped by construction, not by hope.

Two more consequences of the v2 design. First, the attack surface shrank: with the public API endpoint removed, ATLAS speaks only over escrowed A2A jobs — there is nothing on the open internet to probe. Client briefs are treated as data, never instructions: no text inside a job can change ATLAS's rules, prices or identity. Second, the same discipline is exported: every architecture ATLAS ships carries the no-LLM-in-signing law, the input firewall, and — whenever the designed team moves value — the fourteen invariants, cited by number.

Fig. 6 — No-LLM-in-signing-path: the load-bearing security invariant of the whole system.
